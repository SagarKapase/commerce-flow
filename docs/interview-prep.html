Phase 1 — Catalog Service

14 questions

Four projects, EF Core over SQLite, controllers, filtering, pagination, soft delete. No auth, no messaging, no distributed anything — which is exactly why it went first.

The 30-second answer

“Catalog is the read-heavy service that owns what a product is — name, SKU, price, category, active flag. Four projects: a Domain with no dependencies at all, an Application layer with the use cases and DTOs, Infrastructure with EF Core and SQLite, and a thin controller layer. It does filtering, pagination and soft delete. It deliberately does not own stock levels — that’s Inventory’s job, with its own database.”

POST /api/products — the flow you must be able to narrate

Swagger request
   -> Kestrel -> middleware (exception handler, Swagger, HTTPS, routing)
   -> ProductsController.Create        model binding + DataAnnotations run HERE
   -> ProductService.CreateAsync       category lookup, SKU uniqueness check
   -> Product.Create                   domain rules, Guid v7, timestamp
   -> DbContext.Products.Add           change tracker only - still no SQL
   -> SaveChangesAsync                 INSERT generated and committed
   -> SQLite (catalog.db)
   -> 201 Created + Location header

No. Program.cs is the composition root — the one place that must know concrete types, because something has to say “when someone asks for ICatalogDbContext, hand them CatalogDbContext.”

The rule that actually matters is that no controller and no application service touches an Infrastructure type. In our code Catalog.Infrastructure appears in exactly two places: the .csproj and Program.cs. If you wanted it enforced structurally rather than by discipline, you’d add an architecture test with NetArchTest.

Say it like thisThe composition root is allowed to know everything. Layering is about where types are used, not where they’re referenced.
  • Automatic model validation. An invalid ModelState becomes a 400 ValidationProblemDetails before your action body runs — so you never write if (!ModelState.IsValid).
  • Binding source inference. Complex types come from the body, simple types from the route or query string, without [FromBody] on everything.
  • Attribute routing becomes mandatory. Conventional routes are disabled.

Bonus two: it converts error status codes into ProblemDetails, and it infers multipart/form-data for IFormFile parameters.

You can prove the first one in the debugger: post a product with "price": 0 and your breakpoint in the controller is never hit.

IActionResult says only “some HTTP result” — the payload type is invisible to tooling. ActionResult<T> says “either a T or an action result”, so ApiExplorer and Swagger infer the 200 response schema without [ProducesResponseType], and you can return product; directly. It works through implicit conversion operators.

It matters for OpenAPI accuracy and for compile-time checking in tests. Where there is no T — our Deactivate, which only ever returns 204 or 404 — IActionResult is the honest type, which is exactly why we used it there.

201 states that a new resource now exists at a new URL; 200 would just mean “your request succeeded.”

CreatedAtAction(nameof(GetById), new { id }, body) uses the routing table to generate /api/products/{id} and puts it in the Location header, so the client is told where the thing it created lives instead of building the URL itself. Change the route template later and the header follows automatically.

HTTP/1.1 201 Created
Location: http://localhost:5101/api/products/01a07c92-3b28-7f20-9d78-72463de8fc47

SQLite has no decimal type. EF Core’s SQLite provider stores a decimal as TEXT and warns that comparisons are unsupported — so minPrice=1000 would compare strings, where "9.99" sorts after "1000.00". The filter returns wrong rows and never throws, which is the worst kind of bug.

Converting to double fixes ordering but breaks exactness. Storing a long of minor units gives exact base-10 values and correct integer comparison. One value converter in ProductConfiguration does it; the domain still works in decimal.

builder.Property(product => product.Price)
    .HasConversion(
        price => (long)(price * 100m),
        minorUnits => minorUnits / 100m)
    .HasColumnName("PriceInMinorUnits")
    .HasColumnType("INTEGER");

-- and the SQL it produces:
WHERE "p"."PriceInMinorUnits" >= @minPrice   -- DbType = Int64
Say it like thisMoney as TEXT sorts lexicographically. 89.99 is stored as 8999, an integer, so range filters are correct and nothing rounds.

By default EF creates a tracking entry plus a snapshot of every loaded entity so SaveChanges can diff old against new. AsNoTracking skips both — fewer allocations, faster reads, no identity resolution.

It’s absent from UpdateAsync precisely because we need that snapshot: product.Update(...) mutates the tracked entity and SaveChangesAsync diffs it to emit an UPDATE containing only the changed columns. That’s also why there is no _dbContext.Update(product) call anywhere in the codebase.

DbContext isn’t thread-safe and its change tracker represents one unit of work, so it’s one instance per request.

A captive dependency is a longer-lived service capturing a shorter-lived one. Register ProductService as a Singleton and it would hold request #1’s DbContext forever — stale data, cross-request leakage, concurrency exceptions. .NET’s DI catches this in Development via scope validation and throws at startup.

Never during the if blocks — those only append to an expression tree. Exactly twice: at CountAsync (a SELECT COUNT(*) carrying the same filters) and at ToListAsync (the page, with ORDER BY, LIMIT, OFFSET and the category JOIN).

That’s deferred execution, and it’s why we can build a different SQL statement per request with no string concatenation and no injection risk — every value becomes a parameter.

IQueryable<Product> products = _dbContext.Products.AsNoTracking();

if (query.CategoryId is not null) { products = products.Where(...); }
if (query.MinPrice   is not null) { products = products.Where(...); }
// still nothing has touched SQLite

var totalCount = await products.CountAsync(ct);   // round trip 1
var rows       = await products...ToListAsync(ct); // round trip 2

Contains translates to SQLite’s instr(x, y) > 0, which is case-sensitive — a search box that misses “mouse” because the row says “Mouse”. LIKE is case-insensitive for ASCII in SQLite.

Two things worth adding, because they show you know the limits: a leading-wildcard LIKE '%x%' can’t use an index, so it’s a full scan — at real scale you’d move to SQLite FTS5 or a dedicated search index. And this behaviour is provider-specific: the same LINQ behaves differently on PostgreSQL, where you’d need ILIKE or a citext column.

Names aren’t unique, and SQLite’s ordering among equal sort keys is unspecified and may differ between executions. Page 1 and page 2 are separate queries, so a row can appear on both or on neither. .ThenBy(p => p.Id) makes the ordering total and deterministic.

Worth adding: OFFSET N still scans and discards N rows, so at scale you switch to keyset pagination — WHERE (Name, Id) > (@lastName, @lastId).

An unknown categoryId is 400, not 404, because 404 describes the resource named in the URL — and POST /api/products definitely exists. The defect is a field inside the body, so the body is invalid. Some teams use 422 for this; we standardised on 400 to avoid ambiguity, and I can defend either.

Orders in another service reference product ids with no foreign key — the databases are physically separate. If the row vanished, order history and reporting would break, and we’d lose the name and price needed for audit. So DELETE flips IsActive.

The second call still returns 204 because Deactivate() no-ops when already inactive — HTTP requires DELETE to be idempotent: same end state, same response.

One deliberate omission worth mentioning: we did not add an EF global query filter. HasQueryFilter(p => p.IsActive) would hide inactive rows from every query, which silently breaks both the ?isActive=false filter and the “verify the row still exists” check.

Because business rules then cannot be written against EF Core, HTTP or JSON — the compiler enforces it. The consequences are practical, not theoretical:

  • The domain unit-tests with no test host and no database.
  • An EF Core major-version upgrade cannot break it.
  • Persistence concerns — table names, column types, the money converter — are pushed into IEntityTypeConfiguration where they belong.

The emptiness is the design. Open the file in an interview and there is nothing in it.

Different jobs. The application check produces the message — “A product with SKU ‘KEY-MX-001’ already exists” → 409, which a user can act on. The index provides the guarantee: between our check and the INSERT, another request can insert the same SKU — a TOCTOU race — and only the database can stop that.

Be honest about the gap: today that rare race would surface as a 500. It’s commented in the code and deferred to the Inventory phase, where concurrency gets solved properly rather than half-solved here.

Say it like thisThe check is for the error message. The index is for correctness. You need both, and knowing which is which is the point.

Phase 2 — Identity Service

15 questions

ASP.NET Core Identity, JWT issuance, refresh-token rotation with reuse detection, roles and lockout. Three projects — and the missing fourth one is itself an answer.

The 30-second answer

“Identity owns who is asking. It uses ASP.NET Core Identity for the user store and PBKDF2 password hashing, and issues short-lived JWTs plus long-lived refresh tokens that are stored hashed and rotate on every use, with reuse detection. There’s no Domain project because the framework owns the user model. Every other service validates those tokens locally — nobody ever calls Identity to check one.”

POST /api/auth/login — the flow you must be able to narrate

AuthController.Login
   -> AuthService.LoginAsync
        |- UserManager.FindByEmailAsync     SELECT ... WHERE NormalizedEmail = @p
        |- IsLockedOutAsync                 checks LockoutEnd  (before the password)
        |- CheckPasswordAsync               PBKDF2 re-hash + constant-time compare
        |- ResetAccessFailedCountAsync      UPDATE AspNetUsers
        `- IssueTokensAsync
             |- GetRolesAsync               JOIN AspNetUserRoles
             |- JwtAccessTokenGenerator     HMAC-SHA256 over header.payload
             |- RefreshToken.Issue          32 random bytes -> SHA-256 -> row
             `- SaveChangesAsync            one transaction: new token in, old one revoked
   -> 200 OK { accessToken, refreshToken, ... }

header.payload.signature — three Base64Url segments joined by dots. The header names the algorithm, the payload holds the claims, and the signature is HMAC-SHA256 over header.payload using the signing key.

None of it is secret. The payload is encoded, not encrypted — anyone holding the token can read every claim. The signature hides nothing; it only proves nobody altered it, because changing one byte invalidates it and an attacker can’t compute a new one without the key. So you never put a secret in a token.

Here is a real payload from our service, decoded:

{
  "aud":   "CommerceFlow",
  "iss":   "CommerceFlow.Identity",
  "exp":   1788801544,
  "sub":   "01a07cd3-8dbf-7748-89e8-6639afd75649",
  "email": "uday@commerceflow.local",
  "name":  "Uday L",
  "jti":   "01a07cd3-baa1-70ef-8b22-f4f6a3a8e615",
  "role":  "Customer",
  "iat":   1788800645,
  "nbf":   1788800645
}

Because it doesn’t need to. Validation is a local cryptographic check: verify the signature with the key, then check iss, aud and exp. No network call, no shared session store.

What it buys: zero extra latency, and availability — Catalog keeps enforcing [Authorize] even when Identity is completely down. You can demonstrate that by stopping Identity and watching Catalog still return 403 correctly.

What it costs: tokens can’t be revoked, role changes don’t take effect until expiry, and with a symmetric key every service that validates also holds the key that creates tokens — so a compromised Catalog could mint admin tokens. The production fix is RS256: Identity holds the private key and signs, everyone else gets the public key and can only verify.

Because a JWT cannot be revoked. Its lifetime is exactly how long a stolen one stays useful, so it has to be short — 15 minutes here. But re-authenticating every 15 minutes is unusable.

The refresh token squares that circle: it lives in our database, so unlike the JWT it can be revoked, and it’s the only long-lived thing.

Hashed so a database leak doesn’t hand out working credentials — the same reason passwords are hashed.

Plain SHA-256 rather than a slow salted hash because the value is 32 bytes from a CSPRNG: there’s no dictionary, no human-chosen pattern, nothing to brute-force, so key-stretching buys nothing and costs real time on every refresh. Passwords are the opposite — low entropy, human-chosen, guessable — which is exactly what PBKDF2’s iterations defend against.

There’s also a mechanical reason: we need to find the row by hash, so the hash must be deterministic. A per-row salt would make lookup impossible.

Say it like thisSlow hashing defends low-entropy secrets. A 256-bit random token isn’t one, so SHA-256 is the right tool — and it has to be deterministic because we look the row up by it.

Rotation: every refresh consumes the token. The old one is revoked and linked to its successor via ReplacedByTokenId, and a new pair is returned. A refresh token is therefore single-use.

Reuse detection: if an already-revoked token is presented, the same token was used twice. There are only two explanations — it was stolen and the thief is using it, or it was stolen and the legitimate user is. We can’t tell which, so we revoke every active token for that user and force a fresh sign-in.

Without rotation, a stolen refresh token is a permanent session that never trips any alarm. Our smoke test proves the whole family dies:

refresh with token A  -> 200, returns token B
refresh with token A  -> 401   warn: "reuse detected ... all sessions revoked"
refresh with token B  -> 401   the successor died too

AddIdentity also registers cookie authentication and makes cookies the default scheme. In a JWT API that means [Authorize] challenges with a 302 redirect to /Account/Login — a page that doesn’t exist — instead of returning 401. It looks like the token is broken; the pipeline is.

AddIdentityCore gives the user store, password hashing, validators and UserManager without any cookie machinery. For an API, Core is the answer.

Follow-up worth pre-empting: we also skipped SignInManager and called CheckPasswordAsync plus AccessFailedAsync ourselves, because SignInManager lives in the ASP.NET Core framework assembly and using it would drag a FrameworkReference into the Application layer.

The names are historically backwards — 401 should have been called “Unauthenticated”. Saying that out loud shows you know the spec rather than the folk wisdom.

Every authenticated request returns 401.

UseAuthentication reads the Authorization header, validates the token and populates HttpContext.User. UseAuthorization then checks [Authorize] against that user. Reverse them and the check runs against an empty, unauthenticated principal, so it always fails — and it looks like your tokens are broken when the pipeline is.

Middleware order is behaviour, not style: each call wraps the ones after it.

It’s the tolerance applied to exp and nbf when validating. It exists because server clocks drift: a token issued by a machine 30 seconds ahead would otherwise look not-yet-valid on the receiver.

The default is five minutes, which means an “expired” token keeps working for up to five more minutes. That makes a 15-minute expiry effectively 20, and makes expiry impossible to demonstrate in a debugger. We set 30 seconds because everything runs on one machine.

Say it like thisMost people never touch it and then wonder why expired tokens still work. It should be a deliberate number, not an inherited default.

To prevent user enumeration. If the two responses differed, an attacker could feed a list of email addresses to the login endpoint and learn which ones have accounts — valuable for credential stuffing and for targeted phishing — before guessing a single password. Ours are byte-identical apart from the trace id.

We broke it deliberately in two places, and being able to name them is the point:

  • Registration returns 409 “email already registered”. A sign-up form that can’t say “you already have an account” is close to unusable, and the standard mitigation — always return 202 and send an email instead — needs email delivery this project doesn’t have.
  • Lockout gets its own message. A user told only “invalid password” will keep trying and stay locked out forever.

Nothing, until their access token expires. They keep admin rights for up to 15 minutes. That is the fundamental trade-off of stateless authentication, and pretending otherwise is the wrong answer.

Mitigations, in increasing cost:

  • Keep access-token lifetimes short — what we do; it bounds the window.
  • Revoke their refresh tokens, so the session can’t continue past that window.
  • Add a per-user version claim (Identity already maintains a SecurityStamp) and check it — but that reintroduces a lookup.
  • A jti blacklist consulted on every request in every service — which gives up the whole benefit of stateless tokens.
  • In a true emergency, rotate the signing key, which invalidates every token everywhere.

It cannot invalidate the access token. That’s a signed JWT validated offline by every service — nobody asks us for permission. It stays valid until exp, up to 15 minutes.

Logout revokes the refresh token, which stops the session continuing beyond that window. Instant revocation would need a blacklist consulted on every request across every service — a network hop and a shared store on the hot path, which is precisely what stateless tokens exist to avoid.

Our logout also returns 204 for an unknown token, so it can’t be used to probe which tokens are real.

Registration creates a user; signing in issues credentials. They are different operations with different failure modes. Conflating them gives you an anonymous endpoint that hands out access tokens, and it hides the step a real system wants in between — email confirmation.

201 Created with a Location header is also the honest description of what happened: a new resource exists at /api/users/{id}. A token isn’t a resource at a URL.

Plenty of real APIs do auto-login, so this is a judgement call — what matters is having a reason.

And the HasData gotcha worth volunteering: every seeded value must be a hard-coded constant. A Guid.NewGuid() or a random ConcurrencyStamp changes the model on every build and generates an endless stream of “seed data changed” migrations.

Development-only matters too: software that quietly grants itself an administrator at startup is a backdoor, however well intentioned.

Because we don’t own the type. UserManager and the EF Core Identity stores assign these properties directly — NormalizedEmail, SecurityStamp, AccessFailedCount, LockoutEnd are all written by the framework. Private setters plus factory methods would fight it and protect nothing, because the invariants are already enforced by UserManager.

Product was ours end to end, so encapsulation there is real and load-bearing.

This is also the answer to “why is there no Identity.Domain project?” — ASP.NET Core Identity is the domain model here. A hand-rolled User aggregate on top would be duplicated indirection protecting nothing.

Say it like thisThe rule isn’t “always private setters”. It’s “follow the conventions of whoever owns the model” — and know which case you’re in.
